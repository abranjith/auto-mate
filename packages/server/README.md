# @automate/server

The local Express API, embedded SQLite storage, disclosure gate, provider sessions, and resumable conversation transport for the developer preview.

From the repository root, run `pnpm install`, `pnpm doctor`, then `pnpm --filter @automate/server dev`. The server listens on `127.0.0.1:4317` by default. `AUTOMATE_HOST`, `AUTOMATE_PORT`, `AUTOMATE_HOME`, `AUTOMATE_MAX_CONCURRENT_EXECUTIONS` (provisional default `1`), `AUTOMATE_ALLOWED_ORIGINS`, and `LOG_LEVEL` are optional overrides.

Disclosure and clarification add four provisional D14 limits: `AUTOMATE_MAX_WAITING_EXECUTIONS` (default `5`), `AUTOMATE_MAX_AGENT_CLARIFICATIONS` (default `3`), `AUTOMATE_MAX_PREFLIGHT_DECISIONS` (default `3`), and `AUTOMATE_MAX_DIAGNOSTIC_BYTES` (default `8192`). These are operating defaults, not validated product limits.

`GET /api/health` reports server and database status. Errors use `{ "error": { "code", "message", "correlationId" } }`. `AppMetaRepository` owns access to `app_meta`; migrations are generated offline with `pnpm db:generate` and applied automatically on startup. Storage defaults to `~/.automate/`.

Use `pnpm --filter @automate/server test` and `pnpm --filter @automate/server typecheck` during development. Tests use temporary databases.

## Agent provider

`src/agent/index.ts` is the **only** agent module the rest of the server imports. It exposes `createAgentProvider(deps)`, the `AgentConfigStore`, `probeProviders`, `runAgentSmoke`, and the in-memory `FakeAgentProvider` that later features' tests build on.

`@earendil-works/pi-coding-agent` (pinned exactly at `0.87.1`) may be imported **only** under `src/agent/adapters/pi/`. An ESLint `no-restricted-imports` rule and the source-text scan in `src/__tests__/agent-boundary.test.ts` both enforce that; a deliberate-violation fixture exists so each guard can be proven to fail.

The adapter builds its Pi environment against pinned paths under the application data root, with `allowModelNetwork: false`, in-memory settings, and a resource loader that yields zero extensions, skills, prompt templates, themes, and context files. `enumerate()` is the assertable evidence for that claim.

Agent endpoints: `GET`/`PUT /api/agent/config`, `GET /api/agent/providers`, and `POST /api/agent/test-connection`. None of them returns a credential value. `pnpm --filter @automate/server doctor --agent-smoke` opens one real session end to end.

See [AI provider configuration](../../docs/features/provider-configuration.md) for the full reference.

## Task conversations

`src/conversation/` owns the provider-backed `TaskSession`, the live-session registry, assistant-text coalescing, and browser-safe presenters. `src/db/repositories/` is the only data-access path for tasks, executions, and the append-only conversation transcript. Startup reconciles stale active executions before listening and drains live sessions during shutdown.

REST creates tasks, reads task/execution state, replays events, and aborts runs. `src/ws/` attaches a server-to-client WebSocket at `/api/ws/executions/:id?afterSeq=N` for a snapshot plus live tail. State-changing REST routes and WebSocket upgrades validate `Origin` and `Host`; these are local-access controls, not generated-code isolation.

See [Task Description and Conversation Surface](../../docs/features/task-conversation-surface.md) for endpoints, messages, close codes, recovery outcomes, and limits.

## File ingestion

`src/ingestion/index.ts` is the only ingestion module routes and startup import. It holds:

- `upload-intake.ts`: `busboy` multipart intake. It streams one file to disk while counting, hashing, and probing it, and aborts the moment `AUTOMATE_MAX_UPLOAD_BYTES` is passed.
- `upload-file-store.ts`: every upload path, built with `resolveWithin` from sanitized names.
- `csv-reader.ts` and `xlsx-reader.ts`: streaming readers. Workbooks use exceljs's streaming reader only, guarded by inflation and shared-string budgets.
- `profile-service.ts`: read, profile, and persist under `AUTOMATE_PARSE_TIMEOUT_MS`.
- `upload-service.ts`: receive, describe, delete, and attach inside task creation.
- `staged-upload-sweeper.ts`: orphan cleanup at startup and hourly.

Profiling itself is pure code in `@automate/core`. Nothing in `src/ingestion/` imports the agent layer or makes a network call, and `src/__tests__/ingestion-boundary.test.ts` enforces both.

Endpoints: `POST /api/uploads`, `GET`/`DELETE /api/uploads/:id`, `GET /api/tasks/:taskId/uploads`, and `uploadIds` on `POST /api/tasks`.

Limits, all provisional (D14): `AUTOMATE_MAX_UPLOAD_BYTES` (50 MB), `AUTOMATE_MAX_FILES_PER_TASK` (5), `AUTOMATE_MAX_PROFILE_ROWS` (1,000,000), `AUTOMATE_MAX_COLUMNS` (512), `AUTOMATE_PARSE_TIMEOUT_MS` (60000), `AUTOMATE_MAX_SHEETS` (20), `AUTOMATE_MAX_INFLATED_BYTES` (1 GB), and `AUTOMATE_STAGED_UPLOAD_TTL_HOURS` (24).

The ingestion fixture corpus is generated by `src/__tests__/fixtures/ingestion/corpus.ts` and driven end to end by `src/__tests__/ingestion-e2e.test.ts`. See [CSV and XLSX Ingestion and Profiling](../../docs/features/csv-xlsx-ingestion.md).

## Disclosure and clarification API

`GET /api/disclosure/preview?uploadIds=1,2` returns the exact text, digest, recipient, required decisions, applied defaults, and truncation notes. `POST /api/disclosure/consents` re-derives that preview and persists an approval only when the digest still matches. `POST /api/tasks` then requires `disclosureAck` and all required `preflightDecisions` whenever uploads are present. A changed payload, provider, model, or scope reopens the gate.

`GET /api/executions/:id/disclosure` returns transmission receipts and exact approved bytes. `GET /api/executions/:id/clarifications` replays question batches; `POST /api/clarifications/:id/answers` answers a pending batch atomically. Errors use `DISCLOSURE_CONSENT_REQUIRED`, `DISCLOSURE_CONSENT_STALE`, `DISCLOSURE_SCOPE_NOT_GRANTED`, `PREFLIGHT_DECISION_REQUIRED`, `CLARIFICATION_NOT_FOUND`, `CLARIFICATION_NOT_PENDING`, `CLARIFICATION_INVALID_ANSWER`, `CLARIFICATION_LIMIT_REACHED`, and `WAITING_CAPACITY_REACHED`.

`DisclosureRunStrategy` reads the approved snapshot rather than rendering again, records a context receipt before opening the provider, and registers `request_clarification`. A waiting execution frees its normal concurrency slot, remains cancellable through the existing abort route, and is reconciled honestly after restart.

## Code generation and the repair loop

`src/generation/index.ts` is the only generation module routes and startup import; `createGenerationStack` composes it. `CodeGenerationRunStrategy` wraps `DisclosureRunStrategy` for tasks with files: it verifies consent before writing anything, writes synthetic fixtures, adds the code contract to the same prompt, and registers `write_script`, `write_test`, `run_tests`, and `finalize_script` beside `request_clarification`. The agent still has no filesystem, shell, or network tool. Text-only tasks pass straight through to `DisclosureRunStrategy`.

- `code-workspace.ts` stores every file in the execution's draft `code_version`, seals it with a SHA-256 over its file set, and writes the files to `scripts/{executionId}/attempt-{n}/` from the stored rows. The database is authoritative; deleting `scripts/` loses nothing but time.
- `fixture-service.ts` builds each fixture from the approved disclosure payload and writes it to `scripts/{executionId}/fixtures/<stored filename>`. It never opens an upload's stored bytes, and `src/__tests__/generation-e2e.test.ts` has a guard that proves it.
- `tools/run-tests-tool.ts` claims an attempt, checks the diagnostics consent, prepares the Python environment, seals, runs pytest, and sends failure output to the model only through `recordDiagnosticTransmission`. A refusal is recorded and returned, never thrown.
- `generation-budget.ts` counts attempts from the database and keeps the wall clock, paused while the run waits for a person's answer, plus the optional spend cap. `generation-lifecycle.ts` decides how a run settles and appends the one `generation_settled` event.

`src/execution/` holds the production `PythonRunner` behind the unchanged three-method seam. `runtime-provisioner.ts` copies committed manifests, installs the pinned interpreter when missing, and prepares `env/` with `uv sync --locked`. `uv-python-runner.ts` runs generated tests with `uv run --no-sync --locked -- python -m pytest`; approved scripts use the app-owned absolute launcher. `process-runner.ts` bounds captured output and kills the process tree on timeout, cancel, or output growth. `dependency-policy.ts` fixes these script packages: `pandas`, `openpyxl`, `xlsxwriter`, `plotly`, `matplotlib`, `jinja2`, `python-dateutil`, `pytest`. The lock and pins prevent dependency drift. They do not restrict network or file access; generated code runs with this server's access to the computer.

Limits, all provisional against open D14, as environment variables: `AUTOMATE_MAX_GENERATION_ATTEMPTS` (default `3`), `AUTOMATE_GENERATION_TIMEOUT_MS` (`600000`), `AUTOMATE_MAX_GENERATION_COST_USD` (`0`, which turns the cap off), `AUTOMATE_TEST_RUN_TIMEOUT_MS` (`120000`), `AUTOMATE_UV_SYNC_TIMEOUT_MS` (`300000`), `AUTOMATE_FIXTURE_ROW_COUNT` (`200`), and `AUTOMATE_MAX_SCRIPT_BYTES` (`262144`).

Endpoints: `GET /api/executions/:id/code-versions`, `GET /api/code-versions/:id`, `GET /api/executions/:id/attempts` (with the limits), `GET /api/executions/:id/fixtures`, and `POST /api/executions/:id/retry`, which is Origin-guarded. Errors: `GENERATION_ATTEMPTS_EXHAUSTED`, `GENERATION_TIMEOUT`, `GENERATION_COST_LIMIT`, `CODE_VERSION_NOT_FOUND`, `CODE_VERSION_IMMUTABLE`, `CODE_VERSION_NOT_FINAL`, `INVALID_CODE_PATH`, `CODE_TOO_LARGE`, `PYTHON_RUNTIME_UNAVAILABLE`, `FIXTURE_GENERATION_FAILED`, and `EXECUTION_NOT_RETRYABLE`.

Tests use `FakeAgentProvider` scripted with tool-call steps and `FakePythonRunner` (`src/execution/testing/`); no generation test starts a real process or reaches the network. `src/__tests__/support/generation-harness.ts` wires the whole stack against a temporary data root. See [Code Generation and Repair](../../docs/features/code-generation-repair.md).

## Verification, the approval gate, the real run, and the review

`src/verification/index.ts` is the only verification module routes and startup import. `createVerificationStack` composes it. Nothing in `src/verification/` or `src/execution/` opens a provider session or builds a prompt; `src/__tests__/verify-execute-review-e2e.test.ts` scans for it.

- **Hand-off.** When a generation run finalizes a version, `GenerationLifecycle` settles `verifying` rather than `completed`. `TaskSessionRegistry.onHandOff` then starts a verification pass. Verification passes and real runs are `PhaseJob`s in the registry: they count against `AUTOMATE_MAX_CONCURRENT_EXECUTIONS` and cancel through the existing `POST /api/executions/:id/abort`. The registry is also each execution's event fan-out, and the WebSocket subscribes there, so events published after the provider session closes still reach an open page.
- **Checks.** `verification-pass.ts` runs seven checks in order: `integrity`, `contract_entrypoint`, `contract_inputs`, `contract_outputs`, `lint`, `security`, and `tests`. It stops early only when integrity fails, and writes every check it did not run as `skipped`. `@automate/core`'s `decideGate` alone decides whether the run may proceed.
- **Checker environment.** `verify-env.ts` uses the committed checker lock: `ruff` 0.16.9 and `bandit` 1.9.4 in `~/.automate/verify-env/`. They run from that directory with `ruff --isolated` and `bandit -c verify-env/bandit.yaml --ini verify-env/bandit.ini`, so configuration placed beside generated code is not read. This is hygiene, not isolation.
- **Binding.** `runtime-probe.ts` fingerprints the script environment with one `PythonRunner.run` call: Python and every package, plus the uv version, platform, and checker versions. A `verification_run` stores that fingerprint and the code digest. `UNIQUE(code_version_id, runtime_fingerprint)` makes an unchanged pair reuse its verdict.
- **Gate.** `run-intent-service.ts` builds what the gate shows from stored rows only. `approval-service.ts` rejects a stale intent digest, returns the run to `verifying` when the runtime moved, and requires acknowledged warnings. It records the approval and the state change in one transaction.
- **Run.** `src/execution/script-run-service.ts` stages verified copies of the uploads (`input-stager.ts`, the one module allowed to read an upload's bytes) into `runs/{executionId}/input/`. It recomputes the code digest, re-probes the runtime, and inserts the run row only through `ScriptRunRepository.openGated`, which compares both against the approval, before anything is spawned. Exit 0 with a valid `manifest.json` and every declared file present settles `awaiting_review`. Captured `stdout`/`stderr` is kept head and tail in `script_run` and never logged. The script's copy of the file guards against a buggy script only; generated code can still reach other files on this computer.
- **Review.** `review-service.ts` accepts (`completed`) or rejects (`rejected`, the feedback stored, and a new `trigger = 'feedback'` execution seeded through `GenerationService.retry`).
- **Restart.** `awaiting_approval` and `awaiting_review` survive a restart. `pending`, `generating`, `verifying`, `executing`, and `waiting` are marked interrupted, and their running child rows are settled `aborted` first.

Limits, all provisional against open D14: `AUTOMATE_VERIFICATION_TIMEOUT_MS` (default `300000`), `AUTOMATE_LINT_TIMEOUT_MS` (`60000`), `AUTOMATE_SECURITY_TIMEOUT_MS` (`120000`), `AUTOMATE_SCRIPT_RUN_TIMEOUT_MS` (`900000`), `AUTOMATE_MAX_RUN_OUTPUT_BYTES` (`1048576`), and `AUTOMATE_MAX_REVIEW_FEEDBACK_CHARS` (`2000`). The test re-run reuses `AUTOMATE_TEST_RUN_TIMEOUT_MS`.

Data root additions: `verify-env/` (the checker project) and `runs/{executionId}/` with `input/`, `output/`, and `verify/`. Nothing purges `runs/` yet (D12 is open).

Endpoints: `GET /api/executions/:id/verification`, `POST /api/executions/:id/verify`, `GET /api/executions/:id/intent`, `POST /api/executions/:id/approval`, `GET /api/executions/:id/run`, and `POST /api/executions/:id/review`. The three POSTs are Origin-guarded, like `abort`. No response contains an absolute path. Errors: `VERIFICATION_NOT_FOUND`, `VERIFICATION_STALE`, `VERIFICATION_BLOCKED`, `EXECUTION_NOT_APPROVED`, `APPROVAL_INTENT_MISMATCH`, `APPROVAL_STALE`, `RUN_NOT_FOUND`, `RUN_OUTPUT_MISSING`, `CHECKER_UNAVAILABLE`, `REVIEW_NOT_PENDING`, and `INPUT_COPY_MISMATCH`.

Migration `20260925161513_equal_synch` rebuilds `execution` and `conversation_event`. `migrateDatabase` turns foreign keys off before drizzle opens its transaction: inside a transaction the pragma is ignored, and `DROP TABLE execution` would cascade-delete every child row. The migration ends with a `foreign_key_check` guard that rolls it back on any orphan. Tests use `FakeRuntimeProbe` and `FakeCheckerEnvironment` (`src/verification/testing/`) and `src/__tests__/support/verification-harness.ts`. See [Verification and the Execution Gate](../../docs/features/verification-execution-gate.md).

## Locked Python runtime

`packages/server/runtime/script-env/` and `runtime/verify-env/` commit `pyproject.toml`, `uv.lock`, and `.python-version`. `pnpm runtime:lock` is the maintainer command that regenerates both locks after a deliberate policy change. The app copies them under `env/` and `verify-env/` in the data root, installs CPython 3.14.6 through uv if needed, and runs `uv sync --locked`. It never resolves a new lock on a user's machine. `env/automate_launch.py` is the copied, digest-checked launcher. Both environments have a `.venv/` managed by uv. The first preparation downloads the interpreter and wheels; the duration depends on the connection and host. A ready row means the committed files were copied, the interpreter and packages were checked, and the launcher's digest was stored.

The fixed script set is `pandas`, `openpyxl`, `xlsxwriter`, `plotly`, `matplotlib`, `jinja2`, `python-dateutil`, `pytest`; the checker set is `ruff`, `bandit`. The exact versions are in `src/execution/dependency-policy.ts` and the committed locks. The interpreter is pinned to 3.14.6 because uv 0.11.32 can provision it on the supported hosts; Python.org's newer 3.14.7 had no uv-managed Windows download at implementation time.

`GET /api/runtime` reports both environments, their status, packages, short lock digest, preparation time, and platform capability sentences. `POST /api/runtime/prepare` accepts `{ "kind": "script" }` or `{ "kind": "verify" }`; it is Origin-guarded and shares in-flight preparation. Neither response includes an absolute path. New runtime errors are `RUNTIME_NOT_PREPARED`, `RUNTIME_PREPARE_FAILED`, `RUNTIME_LOCK_MISMATCH`, `LAUNCHER_INTEGRITY`, `SCRIPT_LIMIT_EXCEEDED`, and `NON_PYTHON_ENTRYPOINT`. A lock mismatch is a build problem for the maintainer, not a setting on the user's computer.

These nine controls are **provisional against open D14**. Set them before starting the server:

| Variable | Default | Effect |
| --- | ---: | --- |
| `AUTOMATE_RUNTIME_PREPARE_ON_STARTUP` | `true` | Start non-fatal preparation after the HTTP listener binds. |
| `AUTOMATE_SCRIPT_RUN_TIMEOUT_MS` | `900000` | Kill a real run after 15 minutes on every platform. |
| `AUTOMATE_SCRIPT_MEMORY_LIMIT_BYTES` | `4294967296` | Set a 4 GiB `RLIMIT_AS` on macOS/Linux; `0` disables it. No memory cap is enforced on Windows. |
| `AUTOMATE_SCRIPT_MAX_OUTPUT_FILE_BYTES` | `536870912` | Stop a file write past 512 MiB; POSIX also sets `RLIMIT_FSIZE`. `0` disables it. |
| `AUTOMATE_SCRIPT_MAX_OUTPUT_TOTAL_BYTES` | `1073741824` | Stop when output files total more than 1 GiB; `0` disables it. |
| `AUTOMATE_SCRIPT_MAX_OUTPUT_FILES` | `200` | Stop when more than 200 files appear; `0` disables it. |
| `AUTOMATE_OUTPUT_WATCH_INTERVAL_MS` | `2000` | Milliseconds between output scans. |
| `AUTOMATE_RUNTIME_PREPARE_TIMEOUT_MS` | `1800000` | Stop a package sync after 30 minutes. |
| `AUTOMATE_PYTHON_INSTALL_TIMEOUT_MS` | `600000` | Stop an interpreter download after 10 minutes. |

`--locked`, `--no-sync`, `PYTHONSAFEPATH`, and the pinned interpreter prevent dependency drift and accidental launcher substitution. They are not a network restriction or sandbox. On macOS and Linux, `RLIMIT_AS` is a real memory cap with equal soft and hard values that an unprivileged script cannot lift; Windows enforces no memory cap. Generated code remains unconfined and can read any file the application can. Restricted execution is required before a target-user pilot; the runner technology is still unselected. Run `AUTOMATE_LIVE_PYTHON=1 pnpm --filter @automate/server test live-runtime` on Windows, macOS, and Linux after changing the runtime.
